# Musegod launch guard

This immutable ERC20 wrapper pins one Doppler Bundler and adds a minimum output and deadline to atomic creation plus first buy. It leaves issuance policy to the application's frozen CreateParams. There is no administrator or rescue path. Donated assets remain locked.

Build and test from this directory:

```sh
forge test -vv
```

Export the reproducible deployment artifact from the repository root:

```sh
node contracts/export-artifact.mjs
```

The exporter compiles the production source closure with Solidity 0.8.24 and requires the creation and runtime bytecode to match Forge exactly. Set `SOLC_PATH` if the compiler is outside Foundry's normal macOS/Linux SVM location. The artifact contains ABI, bytecode, immutable references, compiler input SHA256 and dependency hashes. `MusegodLaunchGuard.compiler-input.json` is the standard JSON source verification input.

OpenZeppelin Contracts 5.7.0 is vendored as its unmodified minimal import closure. Its tarball and every source hash are pinned in `lib/openzeppelin-contracts/dependency-lock.json`; keep these files intact.

The tests use an ABI-compatible mock Bundler to isolate rollback and ERC20 behaviors. They do not prove actual Doppler execution or production readiness. The application fork test supplies the separate real-contract execution evidence.

## Buyback V2

V2 adds `MusegodAssetFeedOracle` and `MusegodBuybackBudgetVault`, and replaces the fee engine and WETH forwarder. The already deployed burn Oracle, canonical Splits Swapper and buyback Executor remain fixed. The historical deployment and compiler artifacts under `artifacts/` are preserved. The V2 manifest also pins the actually observed initial feed description hashes, with their read block; human labels in historical config are not used as on-chain metadata. New compiled artifacts live under `artifacts/buyback-v2/`; `artifacts/buyback-v2-deployment.json` is a pending template until actual deployment receipts and exact runtime verification populate it.

The paths are:

- Eligible pool fees → Engine V2. Claims record only observed manager receipt deltas. `syncUntracked(poolId)` verifies an existing pool and at least its original Engine share before crediting actual balance minus pending to a separate `totalSynced` counter. External pushes and donations are never reported as newly claimed platform revenue. Both managers/pools sharing an asset cannot credit it twice. A balance deficit stops spending that currency, retains its exact pending liability and emits `AssetShortfall`; a currency whose sync reverts (for example an unreadable `balanceOf`) emits `SyncFailed`, distinct from the forwarding-path `ForwardFailed`. Neither undoes actual new claim receipts or the healthy currency's synchronization/forwarding. There is no administrator writeoff or withdrawal. The keeper submits an automatic claim only when a pool has income in a currency without a recorded shortfall: a pool whose only income is in a short currency is left in the managers, while mixed income is still collected (its short-currency part then waits behind the deficit). The upstream manager still collects its two currencies atomically: an issuer-caused transfer failure inside that manager can prevent its whole collection, which this Engine cannot split. New income never enlarges an already open conversion window.
- Priced assets → fixed Kyber router/executor with the unchanged 99% reference floor → Vault. WETH goes directly to Vault; MUSEGOD goes to DEAD. Only originally unpriced assets may go to the existing fixed Automation account. Stale/paused/retired priced assets remain pending.
- Native Automation → its existing source treasury → Forwarder V2 → Vault. Forwarder has no source-account module or arbitrary-call authority, pays no caller reward and rejects any outstanding approval above **2.88 WETH**, including MAX and MAX−1. The fixed ceiling is one day of maximum Vault throughput (`0.01 × 86400/300`), not a larger spending limit or a daily reset. The treasury still signs the actual amount; initial mainnet canary approval remains at most 0.01 WETH, and no live authorization was changed by implementing this ceiling. The old Engine, existing Swapper reserves and third-party direct Swapper deposits are outside this Vault budget. A signed allowance can be revoked and eventually needs replenishment. Its exhaustion pauses this transfer path only.
- Vault → inject exact WETH into canonical Swapper → existing Executor → same-pool swap → exact MUSEGOD increase at DEAD, atomically. Swapper returns to its prior WETH balance. Only this call's surplus goes to the caller; preexisting Vault donations cannot subsidize a loss or be swept. Vault has no owner, rescue, alternate destination, standing approval or upgrade.

Every caller spending V2 Vault funds shares one Vault budget of **0.01 WETH in the last 300 seconds**. A bounded FIFO of occupied seconds plus an incremental total enforces `(now−300s, now]`, including calls across calendar-window boundaries. Same-second calls merge; only expired occupied entries are removed, and a completely expired queue resets in O(1). The queue holds at most 300 distinct live seconds and no longer cold-reads 300 empty slots on every execution. Dense partial expiry can still require bounded prefix cleanup; the tests cover dense queue wrap, exact boundaries, long idle, an independent receipt-model fuzz test and a first-execution gas ceiling. Adding funds does not increase the budget. The pool's spot, 5-minute and 30-minute WETH→MUSEGOD prices must have max/min ≤ 1.02. These are correlated observations of one pool, not independent price sources; the check limits short-lived deviations and does not prove that manipulation is uneconomic. The cap is a user-selected risk bound, not a derived safe amount. Missing observations, no liquidity, failed price checks, stale conversion feeds or unprofitable execution mean waiting and retrying; they do not close unrelated token trading.

The AssetFeedOracle governor is the immutable platform treasury `0xc4F87C3715374445C4657aa14c47CBB339b59d1A`. It may propose/cancel only a replacement feed for an initially priced asset (including ETH/USD). Anyone can activate that exact proposal after **604800 seconds**. Replacement resets the full delay; code, decimals, pinned description, fresh complete positive round and original token pause behavior are checked. Governance cannot add/remove priced classes, relax `maxAge`, ignore issuer pause, move funds or replace targets. Matching metadata is not proof of an honest price: this is explicit reference-price governance. A retired feed can be replaced through this narrow path, while an issuer-paused token stays pending until its issuer permits conversion.

Build and verify locally from the repository root:

```sh
npx tsx scripts/build-buyback-artifacts.ts
forge test --root contracts --match-contract 'Musegod(Buyback|AssetFeedOracle|FeeEngine|WethForwarder).*'
npx tsx --test tests/buyback-engine.test.ts tests/buyback-index.test.ts tests/buyback-keeper.test.ts tests/buyback-deployment.test.ts
npx tsx scripts/run.ts scripts/test-buyback-engine-fork.ts
npx tsx scripts/run.ts scripts/test-buyback-vault-fork.ts
```

The artifact builder recompiles each production source closure using Solidity 0.8.24 and checks exact creation/runtime bytecode against Forge. The fork harness checks upstream chain 4663 but signs only unlocked local chain 31337 transactions; a loopback read-only proxy rejects upstream writes. It preserves current pool history and real dependency code, restores the initial snapshot and records whether settlement actually succeeded or safely waited. Fork-only source impersonation for revocation and finite allowance is explicitly an approval fixture; it does not prove human treasury control or native Automation execution. Evidence is written to `docs/evidence/buyback-v2-fork.json`, never over the historical V1 evidence. The separate `test-buyback-vault-fork.ts` intentionally advances local fork time by 1801 seconds at unchanged spot to exercise successful real-contract settlement. Its `buyback-v2-vault-fixture.json` is an explicit hypothetical stable-market fixture and is never accepted as current-mainnet price, keeper profitability or activation proof.

### Deployment and activation runbook

These are execution instructions, not evidence that a production transaction was signed. Deployment, approvals, source verification submissions, keeper signing and canaries require the separate release authorization. Do not set the pending manifest to verified by editing status alone.

1. Freeze reviewed source hashes, reproducible artifacts and config. Independently review the four new contracts and collect current isolated-fork evidence for actual Doppler fee collection, direct WETH forwarding, conversion safety, source forwarding, settlement safety and cleanup. The deployment script requires the separate `buyback-v2-review.json` and exact artifact/source hash match. A waiting fork is safety evidence only; successful live canary receipts remain an activation requirement.
2. Identify the immutable platform treasury's existing signing route. After the exact graph is deployed and recorded in step 5, prove control with its signed graph-bound `governorControlMessage`; no feed proposal/cancellation transaction is required for activation. An EOA signature must recover exactly to the treasury. A contract treasury must validate its signature through EIP-1271, including its normal multisig encoding; an owner EOA signature alone is insufficient. No new treasury module is installed. This check uses current contract signature authority, so a later signing-policy/owner rotation can require a replacement attestation for the same graph.
3. Verify existing Oracle → Swapper → Executor against the historical source/runtime and immutable bindings; require Swapper owner=0, unpaused, beneficiary=DEAD, MUSEGOD output, fixed Oracle and offer factor 985000. Clear the legacy platform Swapper WETH reserve through its existing fixed settlement path under separate authorization, then record a canonical zero-WETH checkpoint after old Forwarder revocation and before the V2 canary. Activation checks that historical checkpoint; later third-party donations do not invalidate it. The new Vault cannot constrain historical old-Engine pools or funds deposited directly into Swapper, and its cap must never be described as covering those routes.
4. Deploy AssetFeedOracle(governor=platform treasury; fixed initial 37 asset feeds plus ETH/USD), then Vault(WETH,MUSEGOD,old Oracle,old Swapper,old Executor), then Forwarder V2(source treasury,WETH,old Swapper,Vault), then Engine V2(existing initializer,hook,old Oracle,old Swapper,WETH,MUSEGOD,router,router executor,Automation,new AssetFeedOracle,Vault). There is no predicted-address or mutually dependent constructor step. Re-running the deploy script must verify recorded addresses instead of duplicating confirmed deployments; unresolved receipt outcomes require reconciliation first.
5. Record every deployment receipt/block, exact runtime hash, immutable binding, compiler input hash and source-verification result in the V2 manifest. The script's `--verify-only` path reads chain state; missing source verification is submitted only during the authorized `--deploy` flow. The old Engine address must never be configured for new launches. Existing pools retain their original policy; no automatic beneficiary migration or claim that old 28.5% shares can be split is made.
6. From the existing source treasury, sign WETH `approve(oldForwarder,0)` for `0x3B6d01e627Fe6e06C831E0f9f57aC976a88309Ff`, wait for canonical success and read allowance=0. Sign `approve(newForwarder,finiteAmount)` with an explicitly reviewed raw-wei amount no greater than the fixed 2.88 WETH ceiling; the initial mainnet canary approval is at most 0.01 WETH. Verify exact token, spender, amount and source in the receipt and fresh reads. Deployment/runtime verification requires `MAX_ALLOWANCE=2880000000000000000`; contract, server, keeper and graph-bound activation reject MAX, MAX−1 and ceiling+1. Later replenishment needs an actual treasury approval and does not increase the Vault rolling cap. Revoke the new allowance to stop future source forwarding without affecting already committed Vault funds.
7. Verify actual V3 `observe([1800,300,0])`, active liquidity and the three prices immediately before activation. A cardinality setting alone is insufficient. The ring writes at most once per distinct second; use at least 1801 retained observations (2048 or 4096 can provide margin), allow real history to accrue, and recheck actual retained time coverage under load. Increasing capacity is a separately authorized pool transaction, not a fake fork history fixture. Do not reduce the 30-minute window or the 2% check to force a pass.
8. Before enabling the public app and production keeper, execute separately authorized canary contract calls using the recorded runtime-verified graph. Test real finite-allowance source forwarding and **native scheduled Automation** from an actual unpriced fee collection through release → conversion/sweep → source WETH → Forwarder V2 → Vault. Save the Engine `FeesClaimed` receipt and fixed initializer/rehype→Engine net token transfers covering at least the canary input; a donation credited by `syncUntracked` is insufficient. Save matching tx hashes, input/output deltas, scheduler run and the receiver/source addresses. The legacy zero-reserve checkpoint must be from a completed block before the canary Forwarder transaction. A manual transfer, dashboard screenshot or saved rule does not count as scheduler execution. Verify `burn amount at DEAD` separately from ERC20 `totalSupply` (which does not decrease). Do not edit away the activation gate to bootstrap this canary.
9. Using separately approved small funds, obtain a successful Vault settlement receipt and verify exact Vault debit, unchanged Swapper baseline, Executor allowance reset, actual DEAD transfer and caller surplus/gas. Measure gas and current executable sizes; keeper starts at min(Vault available, 0.01 WETH), progressively halves up to 20 candidates and requires a 20% gas-profit buffer. Exercise a larger rejected trade and a changed-price wait without lowering limits. Record same-pool manipulation cost/price-impact estimates at the approved cap without presenting them as an independent price guarantee.
10. Only after the first-launch and automatic-buyback acceptance both pass, publish the V2 graph in server/client config and enable the dedicated keeper. Its wallet must differ from deployment, treasury and Automation accounts. Retain its atomic public transaction journal: unknown broadcast/receipt or noncanonical confirmation stops signing and must be reconciled by hash, nonce, target and calldata before any later signature. Ordinary temporary quote/RPC/price failures wait and retry. A canonically confirmed reverted transaction is recorded as a resolved failure, ends that stale task batch and waits for fresh state/simulation in the next round; its old signed transaction is never rebroadcast. Verify startup, restart and an entire scheduled cycle; contract calls remain permissionless if the hosted keeper stops.

Rollback before launch is to keep the new graph unpublished and keeper stopped. After launch, stop keeper signing and revoke source allowance to prevent new automated source transfers; existing Engine/Vault balances remain bound to the fixed conversion/burn paths. There is intentionally no administrator withdrawal. Emergency application controls affect new platform actions; they do not undo signed on-chain transactions or alter existing immutable pool beneficiaries.

Burn history uses persistent `buyback:index:` checkpoints from the verified Engine deployment block, 64-block confirmation delay, canonical block hashes, exact receipt transfers and deduplication. Each round is bounded to 50 pages of 10 blocks and resumes after the last committed page; a changed checkpoint rebuilds the index. A failed history RPC does not close balance processing. UI shows the scanned range/catch-up state and recent receipts, never an unqualified all-time total from a partial scan.

### One-time activation proof

`deployed_verified` means source/runtime verification only. `verifyFeeEngineRuntime` permits read-only graph inspection; production `verifyFeeEngine` additionally invokes `verifyBuybackActivation`. New pools and keeper activation therefore cannot be enabled by editing a status string. The pending manifest intentionally has no valid activation proof.

The proof schema is exported by `server/buyback-activation.ts`: `GovernorControlProof`, `BuybackActivation`, `NativeAcceptanceProof`. Compute `buybackGraphFingerprint(manifest)` from the seven exact addresses/runtime hashes, all fixed accounts, initial feed-description hashes and approved policy. `governance.controlProof` signs `governorControlMessage(proof)` at a recorded canonical block; `activation` contains the same graph/chain identity, exact old-zero and new-finite Approval receipt references, the legacy zero-reserve checkpoint and native acceptance object. The latter signs `nativeAcceptanceMessage(proof)` and binds rule ID, scheduler run ID, HTTPS evidence URI, evidence-content hash, asset/amount, `feeCollectionTransactionHash`, the release `feeTransactionHash`, and every conversion/sweep/forward/settlement transaction hash. Prepare this public proof for the actual controller to sign through its existing wallet; never copy a private key into a proof file.

Every receipt must be successful, canonical and at least 64 blocks confirmed. The verifier matches WETH Approval owner/spender/value, actual Engine `FeesClaimed` for the fixed initializer/rehype and same asset, manager→Engine net transfers, Engine unpriced release, Automation input/output, source→Vault Forwarder output, Vault→Swapper→Executor input and actual Executor→DEAD MUSEGOD output with matching Swapper Flash and Vault Executed events. Claimed fees must cover at least the canary input, and each manager's net incoming transfer must equal its claimed amount. Collection must precede release; `claimAndForward` may share one receipt only when the counted `FeesClaimed` events have smaller canonical log indices than `UnpricedForwarded`. Release, conversion, forward and settlement otherwise require distinct receipts in block/transaction-index order. Sweep must also be distinct unless an atomic conversion delivers directly to source. The recorded finite approval must precede forwarding in a separate transaction. The canary is at most 0.01 WETH and cannot exceed its finite approval. Changing the graph, proof amounts, scheduler identifiers or receipt hashes invalidates the signed acceptance or exact receipt match.

On-chain transfers cannot independently prove that an external scheduler ran. That part is a deliberate governor-signed external attestation over separately retained native run evidence; a manual transfer, unsigned screenshot or bare `passed` flag is not accepted. Review the referenced evidence against its signed hash before signing. The server does not fetch arbitrary evidence URLs. EIP-1271 authority changes require an attestation valid under the current treasury policy.

The verifier also compares the Engine's historical `totalAutomationForwarded(asset)` immediately before the collection block and at the end of the release block. Every release during that interval must fit within the newly evidenced claimed fees, covering at least the canary input. This prevents reusing a previously spent fee receipt after topping up with a donation. Other releases of the same asset in either boundary block count conservatively; use a separate canary asset or an interval with enough actual claimed fees, and retain access to the historical counter reads.

Actual fee-custody receipts are retained separately in `docs/evidence/buyback-v2-fee-custody.json` from an isolated fork pinned to block 82411009. Both `claimFees` and `claimAndForward` show direct initializer/Rehype→Engine token transfers matching their `FeesClaimed` amounts; the PoolManager is upstream custody, not the sender of these final Engine receipts. The atomic example records the unpriced transfer at log 20, `FeesClaimed` at log 24 and `UnpricedForwarded` at log 31. This confirms the current custody check against actual deployed manager behavior; it is not mainnet execution or native scheduler acceptance.

Once these historical proofs exist, a currently exhausted finite source allowance does not disable the Engine or Vault. Replenishment only resumes source forwarding. A new graph always needs its own proof, and the old Forwarder allowance must still be zero. Any missing, orphaned or mismatched proof keeps new-pool activation closed while the verified runtime graph remains readable.
