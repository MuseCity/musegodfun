### Profile links

- Fields are X, YouTube, TikTok, Telegram and website, all optional; an empty field never renders. Each value is stored as one canonical https URL on its platform's host. - The token detail reads the profile within the pool state read's deadline. When the store fails or misses it, the response carries `profileStatus: "stale"` with the service's last answer and `profileCheckedAt`, or `profileStatus: "unavailable"` when it has none; it never reports the profile as absent, so a launch link the owner replaced or cleared cannot reappear. In production a failed read on a quiet coin therefore usually answers unavailable; a store slower than the 8 s page deadline can keep answering unavailable across retries until it speeds up, since hibernation may discard each late fill. Links show as unavailable rather than showing wrong links. Node tests demonstrate reuse only within one resident service instance, not convergence across hibernation.

**Rules**
- A coin can be bound to one ERC-721 on the coin's own chain. Each NFT gets one coin, ever: once it has a `verified` coin, prepare refuses another with `NFT_ALREADY_LAUNCHED`, also after the NFT is sold.
- The launcher must hold the NFT, or be its delegate.xyz v2 delegate (`0x0000…B493`) with rights `musegod.fun.launch` or unscoped.
- Muses (`0x13Ea3072b7215d4C9c2Ec4f498A08c5825129836`) launch free with any supported pair; picking a Muse selects MUSEGOD as the default pair, which the holder can change (owner, 2026-10-18). Other NFTs pay $10 per launch: exactly 10 USDG (`0x5fc5360D0400a0Fd4f2af552ADD042D716F1d168`), or at least the ETH of a 60-second server quote, sent by the launcher to the operations wallet (`config.treasury`). One payment funds one coin; there are no refunds. A USDG transfer counts only from block 87,500,000. ETH quotes are signed under the plan-attestation key with their own domain and are refused without it. The wallet refuses an ETH quote above 0.05 ETH.
- The database enforces both single-use rules for every writer, so they hold across processes (each server runtime and `npm run nft:reverify`): partial unique indexes on the token records refuse a second coin carrying an already spent `launchFee` transaction hash (in any case), and a second `verified` coin for one NFT (chain id, contract in any case, token id). Rejected and unverified coins never reserve the NFT, and an unconfirmed fee's `feeClaim` is not a spend. SQLite creates the indexes at startup (`server/store.ts`) and refuses to start, naming the coins to resolve, when existing records already break a rule. Supabase gets them, per scope, with the `musegod_nft_guards_ready()` check, from migration `supabase/migrations/20261014120000_nft_single_use_indexes.sql`. NFT mode fails closed without them: while that check is not true (a project without the migration, or an unreadable answer, rechecked every minute), `/config` reports NFT mode off even with the flag on, so a flag-on release fails its runtime check; prepare and launch-fee quotes refuse with `NFT_MODE_DISABLED`, the NFT APIs answer `NFT_MODE_UNAVAILABLE`, and `nft:reverify` exits 1 without reading or writing anything. The same switch, the flag or the guards, stops new signatures: signing an NFT plan prepared while NFT mode was on answers `NFT_MODE_UNAVAILABLE`, before any claim; normal launches are unaffected. Registration of coins already launched is never gated. The in-process registration locks only order decisions within one process. When the database refuses a registration's write, the coin still registers, with the status it would have had: `rejected: fee` (nothing spent) or `rejected: already_launched`. When it refuses `nft:reverify`, the command prints `CONFLICT <NFT key or fee hash> <coin> <other coin>`, leaves the record unchanged and exits non-zero.
- The indexes refuse a second coin only at registration, after both creations are on-chain. So before a real signature (`/api/launch/validate` with `signing`), an NFT plan claims its NFT and, for a paid NFT, its fee payment in the database, all or nothing and atomically across processes, for one signing window (5 minutes) from that validation. A claim belongs to the plan. Another plan holding a live claim is refused with `NFT_LAUNCH_IN_PROGRESS` (the NFT) or `NFT_FEE_IN_USE` (the fee), whatever its intent; an expired claim can be taken over. The one exception is a refresh: a plan whose server-stored `previousPlanId` chain (verified at prepare as the same creator, NFT and fee) reaches the holder takes over the holder's claim, so the plan signed after a first-buy approval, or after a re-confirmed price, goes through, while a second refresh of the same plan is refused. Holding the claim, the plan then re-reads both rules (`NFT_ALREADY_LAUNCHED`, `NFT_FEE_USED`) and is protected for signing; a failure in either frees the claim at once. When the wallet's creation is reported (`/api/launch/track`, or registration), a saved prepare's claims become submitted, never taken over or moved, with the 10-minute recovery window as their safety expiry. A recovered backup may only submit and renew rows its plan already owns, never insert or take a claim. Registration and reconcile may insert or renew claims only when the on-chain transaction sender matches the stored plan's creator; a replay from another sender cannot hold that creator's NFT or fee. Tracking reports success only once that is stored: it retries briefly, then answers 503 with a one-second `Retry-After`, which the client's API layer retries. Each reconcile pass renews the submitted claims of a queued creation that has not settled, while the node still knows the transaction; one it has no trace of (evicted or replaced) lapses within one window, so a lost creation never locks its NFT. **Statuses.** Registration records `nftVerification` once and never blocks on it:
- `verified`: the NFT's one coin; prepare refuses another.
- `rejected` with a reason (`pair`, `fee`, `already_launched`, `not_erc721`, `not_controller`): the coin stays registered and its fees still go to the vault (the treasury view, its balances and the sweep include it), but it has no badge and is never listed as that NFT's coin. `fee` is a definite mismatch (wrong recipient, amount, asset or payer, an invalid quote MAC, a non-plain ETH transfer, a failed transaction, a block below the minimum, a payment already used, or a transaction still in the mempool that can never become the payment: another sender's; an ETH transfer whose quote MAC the platform did not sign, or that is not at least the quoted wei sent plain to the operations wallet, or whose quote's mining window (expiry plus 10 minutes) the chain head has passed; or a USDG `transfer` call to another recipient or of another amount), or a fee transaction the chain still has no trace of 10 minutes after the coin's receipt (no transaction and no receipt, or only a pending transaction that is not a direct USDG `transfer` call, such as a wallet contract's call).

- `NFT_MODE_ENABLED` is protected like the chain signing flags, so a live edit is not overwritten by an unchanged release.
