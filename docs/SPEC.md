No arbitrary contract address or silently refreshed upstream asset becomes an issuance target.

All 198 paired assets have local logos, matched by ticker and the pinned Robinhood contract in `src/lib/asset-logos.json`. Company/fund images use genuine PAIR catalog marks, reviewed financial-market images or current issuer assets. WETH uses the PAIR diamond image, USDG and cbBTC use issuer assets, and MUSEGOD uses the image displayed on the user-selected [Pools token page](https://pools.fun/token/0x0379e228f6887c6f18bf394042ecaf81b308cb2e), matched to its exact contract address and resized without cropping. Vanguard/iShares fund families may share their issuer mark. Original image URLs and SHA-256 hashes are retained; images are validated before use and loaded locally without third-party browser requests. Runtime image failure falls back to a readable ticker. The shared icon is used in issuance, quote summaries, previews, catalog cards and the homepage illustration.

The paired-asset picker groups the pinned list into Stocks, ETFs, Penny stocks and Crypto assets, with an All assets view. Counts derive from the active whitelist. Category and case-insensitive name/symbol/contract search work together; changing filters resets the expanded list without changing the selected quote asset or draft. Cards show the ticker and full asset name, the selected summary remains independent of the filter, and empty results can clear the filters. The homepage quote filter uses the same grouped taxonomy. Before launch, the selected active-chain asset must pass pinned-block symbol, decimals, name and supply reads. Missing values remain unknown; failures block launch. Robinhood ERC20 tokens do not receive Base B20 multiplier or share-equivalent treatment. Runtime selects the proper asset list, contracts, wallet chain and explorer. ## Issuance and trading

The Pinata image-upload change is published on both domains, with real production upload, gateway byte integrity, decoded browser previews and refresh persistence verified. The removed image GET endpoint returns 404. [Acceptance evidence](evidence/token-image-pinata.json) separates production checks from local runtime/browser and injected failure scenarios.

- Fixed supply of 1 billion 18-decimal meme tokens, all offered to the immutable locked Multicurve pool. No team reserve. Ninety percent follows an opening-to-10x valuation curve; ten percent forms the contiguous liquidity tail. Valuation is in paired-token units, not USD or an amount paid at creation.
- Name/symbol, description, optional image and website/X/Telegram links are validated and stored in the immutable token metadata. Token image selection accepts PNG/JPG/WebP/GIF up to 5 MiB, converts to a still WebP of at most 512 pixels per side and 40 KiB, and uploads through the existing same-origin API. The server validates raster headers/dimensions and uploads to public IPFS with Pinata v3 and server-only `PINATA_JWT`, returning `https://gateway.pinata.cloud/ipfs/<CID>`. New uploads require Pinata in every runtime and never fall back to Supabase/local storage. Images load directly from public HTTPS URLs. The product has not formally launched, so Supabase/local image reads, the old GET endpoint and its compatibility code are removed. Server keys never reach the browser. Uploads share the existing 64 KiB body/concurrency limits and are additionally limited to ten per minute per IP. Upload progress blocks review; failed uploads preserve the previous image; changing its URL or clearing the draft invalidates late responses. Public HTTPS image URLs remain supported. Drafts survive refresh; a draft from another deployment or a removed U/PAIR selection cannot retain its unsupported paired asset. Removed selections fall back to WETH without discarding the remaining draft fields. Direct issuance requests and previously prepared unsigned previews using removed assets are rejected, including the final validation before a wallet request. Existing receipts are preserved; unsupported pairs are excluded from the active catalog.
- Preview validates the asset and simulates canonical Airlock creation without signature. Confirmation binds creator, treasury, exact calldata, fee policy and five-minute expiry. Selected provider/account/network and runtime are rechecked before each wallet request.
- Server verifies successful receipt, official Airlock target, matching plan/Create event, supply, locked pool state, dynamic PoolKey and canonical block hash before registration. Registration is idempotent and requires two blocks. Pending registration survives restart; reorgs remove invalid catalog entries. Timeout stays pending.
- Buy/sell quotes use the chain's canonical quoter and actual PoolKey, with native integer precision, minimum output, 60-second expiry and deadline. ERC20 and Permit2 approvals use the exact required amount. Both directions simulate before requesting wallet confirmation. Balances and fee amounts stay in asset units, preserving 6/8/18-decimal precision.
- Launch, approvals, trades and claims save hashes and pending/success/failed/cancelled/replaced state. Receipt/replacement checks and manual hash recovery bind the active chain and deployment. An RPC timeout is not a failed transaction.
- External Doppler links remain pending until each pool's identity, public listing and working quotes are verified; a fork never links to mainnet. Robinhood historical market/holder data is currently explicitly unavailable. Never query Base prices or display a cached Base snapshot for a Robinhood token. On-chain quotes remain functional independently.

## Fee policy

New pools retain `creator-70-musegod-v2`: nominal 1% hook fee plus 0.05% LP fee. Doppler receives 5% of each fee stream; remaining net fees go 70% to the creator and 30% to the platform. The platform reserves 80% of its income for MUSEGOD buybacks and 20% for operations.

| Recipient/use | Basis | Share |
| --- | --- | ---: |
| Creator | Net fees after Doppler | 70% |
| Platform | Net fees after Doppler | 30% |
| Buyback budget | Platform income | 80% |
| Operations | Platform income | 20% |
| Creator / buyback / operations / Doppler | Total fees | 66.5% / 22.8% / 5.7% / 5% |

LP on-chain beneficiaries are 5% protocol / 66.5% creator / 28.5% treasury; hook net beneficiaries are 70% creator / 30% treasury. Controller is dead. The platform's internal 80/20 allocation is a manual budget, not four on-chain beneficiaries or proof of a purchase/burn. Creator and treasury claims are verified separately; overlapping accounts merge without losing shares. Integer rounding is applied per claim and asset without allocating more than actual income.

Existing `musegod-80-v1` and unmarked records retain their original interpretation; no backfilling from current policy. Missing policy or treasury stays unknown. The rewards, issuance, token detail and buyback pages use the same separately labeled net/platform/gross denominators.

Planned MUSEGOD target is Robinhood Chain `0x0379E228F6887c6F18bf394042ECAF81B308cb2e`; planned recipient is `0x000000000000000000000000000000000000dEaD`. Transfers to dead do not reduce ERC20 totalSupply. `/buyback` is a deferred policy/status page. Base quote/preparation/step/track execution APIs return `CROSS_CHAIN_DEFERRED`; no active bridge or burn form remains. Prior receipts are preserved for later work. No new Robinhood buyback execution is implied.

## Wallet and runtime

EIP-6963 multiple-wallet discovery/selection plus legacy injected providers; connect/disconnect, authorized refresh restore, account/network changes, locking, cancellation, duplicate requests and late responses. Connection requires no message signature. Mobile uses the wallet's built-in browser; WalletConnect remains outside scope.

The existing `ENABLE_MAINNET_TRANSACTIONS` opt-in and treasury requirements remain. Actual transactions are confirmed by the selected user wallet. Server RPC proxies always reject transaction submission and signature methods. Every wallet action checks the latest config and provider state; disabling new signing still permits recovery of already broadcast hashes.

Local development retains the single Node runtime. Cloudflare production uses Workers static assets plus one named Durable Object for the shared backend, with the original server-only Supabase storage. Durable alarms replace Node intervals; reconciliation has a 60-second budget between rows. Workers never instantiate the local SQLite store; Durable Object platform storage schedules alarms. Active records use `robinhood`, existing Base history uses `base`, local forks use SQLite directories separated by deployment. Shared CoinGecko quota remains under `base` to prevent budget reset. No database permissions, table schemas or history are weakened/deleted for the chain switch or deployment. Readiness, rate/concurrency limits, bounded request bodies, secret redaction, cleanup, Node graceful shutdown, security headers, error boundary, 404 and backup/restore remain required.
